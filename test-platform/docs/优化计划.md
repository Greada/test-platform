# 全量代码优化计划

> 项目：全功能测试平台
> 制定日期：2026-08-09
> 当前版本：V3.3 + Docker + V4 前端优化
> 部署目标：内部测试环境
> 数据库版本管理：引入 Flyway

---

## 一、优化背景

对全量代码（后端 49 个 Java 文件 + 前端全部视图/组件 + SQL/Docker/Jenkins/Nginx 配置）进行深度审计，共发现 **135 个问题**，分布如下：

| 严重程度 | 后端 | 前端 | 基础设施 | 合计 |
|---------|------|------|---------|------|
| 严重 | 5 | 4 | 5 | **14** |
| 高 | 12 | 12 | 9 | **33** |
| 中 | 18 | 25 | 18 | **61** |
| 低 | 5 | 13 | 9 | **27** |
| **合计** | **40** | **54** | **41** | **135** |

按四个阶段推进优化，每阶段可独立验证、单独提交，便于回滚。

```
阶段一(安全加固) ──┐
                    ├─→ 阶段二(数据/配置治理 + Flyway迁移)
                    │     │
                    │     └─→ 阶段三(性能/架构，依赖creator_id字段)
                    │              │
                    │              └─→ 阶段四(质量/工程化)
                    └─→ (可与阶段二并行启动)
```

> **依赖说明**：阶段一的 IDOR 修复（加 `creator_id`）依赖阶段二的 Flyway 迁移先完成表结构，建议阶段二的 Flyway 迁移优先启动，或与阶段一并行。

## 三、阶段二：数据与配置治理（15 项）

### 2.1 Flyway 迁移（核心）

**步骤**：

1. `backend/pom.xml` 添加 `flyway-core` + `flyway-mysql` 依赖
2. 创建 `backend/src/main/resources/db/migration/` 目录
3. 将现有 SQL 重组为：
   - `V1__init_schema.sql` — 合并 init_v1 + init_v2 + init_v3（补 `test_category` 表 + `test_case.category_id` 列）+ init_v4
   - `V2__seed_data.sql` — 合并 insert_test_case_v1（移除 TRUNCATE，改 INSERT IGNORE）
   - `V3__seed_admin_user.sql` — 合并 init_v3 的 user 部分（统一 admin 密码哈希）
4. `application.yml` 添加 `spring.flyway.enabled: true`、`baseline-on-migrate: true`、`baseline-version: 0`
5. `application-dev.yml` 添加 `flyway.clean-disabled: false`（开发可重置）
6. 删除冗余脚本：`insert_test_case_full.sql`（自测数据单独拆）、`user.sql`（重复）
7. `docker/init/init.sql` 保留但标记为"非 Flyway 备用路径"，修复 ALTER 不可重入（加存储过程守卫）

```
会话 1：

  5. 阶段四 代码质量与工程化（B4.x + F4.x + E4.x + A4.x）
```

### 提交规范

- 每个阶段单独提交，不混合
- 提交信息格式：`[阶段X] 简述`
- 重大改动（如 Flyway 迁移、DTO 层引入）单独提交并详细说明

### 验证方式

- 后端：`mvn package -D"maven.test.skip=true"` 编译通过 + 手动接口测试
- 前端：`npm run build` 构建通过 + 手动页面功能验证
- Docker：`docker compose up -d` 启动成功 + 健康检查通过
- 数据库：Flyway 迁移日志无错误 + 表结构验证

### 风险与回滚

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Flyway 迁移失败 | 应用无法启动 | 保留原 SQL 脚本备份；`flyway.repair` 可修复 |
| IDOR 数据隔离改造 | 现有数据无 creator_id | 迁移脚本设默认值 1（admin），后续新数据正确填充 |
| DTO 层引入 | API 响应结构变化 | 保持 DTO 字段与 Entity 一致，仅裁剪敏感字段 |
| 分页改造 | 前端列表行为变化 | 保留 `listAll` 作为兼容接口，新增 `page` 接口 |
| Element Plus 按需引入 | 全局组件不可用 | 逐步迁移，先用 unplugin 自动导入 |
